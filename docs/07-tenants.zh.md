# 07 — 租户模型：公会特化、Native 与兼容双模式

> 英文版为主文档：[07-tenants.md](07-tenants.md)
>
> 调研于 2026-10。租户 = 团队/公会；模型为玩家公会特化（金库/配额/共享仓库），
> 不是通用组织架构。

## 1. 角色与形态

- 角色：`OWNER`（1 名，金库控制、解散）· `OFFICER`（邀请、按策略审批领料）· `MEMBER`
- native 建队 = 一个原子幂等操作：团队行 + OWNER 成员 + **金库账本账户**
  （`TEAM` 类型，租户=teamId）
- 玩家可属 N 个队；每队对应：金库账户、配额桶（03 §6）、仓库范围（AE2 cell 绑定，02 §2）

## 2. Native vs 兼容模式（同时只激活一个）

| | NATIVE | COMPAT（如 FTBTEAMS） |
|---|---|---|
| 权威 | BRP 后端 | 游戏侧 mod |
| 建/邀/踢 | API（Web 门户 + 终端） | 在对方 mod 里，照旧 |
| 花名册流向 | 后端 → 游戏（P1 UI） | Agent 拉取 → `POST /teams/sync`（只读镜像） |
| Native 端点 | 启用 | **拒绝改写兼容来源的行**（已有测试） |
| 队伍 ID | 自选 | 来源 mod 的稳定 UUID |

同步协议：整批替换、`batchId` 幂等、批内原子；花名册替换保留老成员
`joined_at`，退队即删。

## 3. FTB Teams 兼容（已调研）

- FTB Teams 是事实标准团队 mod（CurseForge 224M+ 下载），1.21.1 NeoForge
  活跃维护；API 经 `maven.ftb.dev.org`（`dev.ftb:ftb-teams-neoforge`）引入
- 入口（◆ 接线时核对）：`FTBTeamsAPI.api().getManager()` →
  `getTeamByID/getTeamByPlayer` → `PartyTeam.getMembers()` → 成员 uuid/角色；
  组队 API 近期变更过（changelog）——以源码为准，别信旧教程
- 第三方集成先例：Better Party X FTB Teams（Modrinth）就是同步
  成员/名字/队长，与我们适配器同一形态
- 映射：FTB party UUID = 后端 team id；owner/officer→OFFICER；单人
  player-team 跳过；兼容模式下 Agent **绝不**反向改 FTB 状态

## 4. 为什么不把 LuckPerms 组当队伍？

LuckPerms = 权限模型（运维关心），FTB/BRP = 社交单元（持久、跨功能）。
LP 组同步进 RBAC（01 §6），不进租户——混这两样正是"企业级"名声的由来。

## 5. 认证边界（用户决策：丢给 MC server）

BRP **不自建玩家认证**：游戏内身份 = MC 服务器会话（在线模式验证；Agent
只为已认证的 `ServerPlayer` 行动）。Web 门户用游戏内发码绑定（短时效，
玩家必须在线）——游戏服是唯一身份权威，BRP 是依赖方。Agent↔Backend 用
实例注册（P1 上 HMAC），那是机器认证，不是玩家认证。

## 6. 审批迷宫（已上线：后端 + 门户）

金库提现流程端到端已通——REST 在 `/api/v1/approvals`，门户审批页带
一键裁决动作：

- OFFICER 在策略内审批；金额达到/超过"高层管理"阈值进入
  `AWAITING_UPPER_MANAGEMENT`，等 OWNER 签字（配置：
  `brp.approval.rubber-stamp-cents` / `upper-management-cents`）
- 橡皮图章阈值内自动批准——官僚体系高效到跳过自己，备忘归档，KPI 达成
- 每次操作追加一条 `approval_action`（SUBMITTED / RUBBER_STAMPED /
  APPROVED / REJECTED / NUDGED）：留痕本身就是产品
- per-my-last-email 催办（`POST /requests/{id}/nudge`）记录升格表演并
  返回一个（就一个）黑话词；投递走 outbox
- 执行跑 `vault-withdraw` saga（冻结 → 发放 → 结算，反向补偿），幂等键由
  requestId 派生——梗给人看，不变量给数据库看

## 7. 村民作为雇员（类别 `VILLAGER`：不交单据，也不涨薪）

EHR 终于有了一群认真对待它的人口。村民以"非玩家雇员"身份进入其 chunk
ticket 所属租户的花名册（09 §3）；HR 的每一件道具游戏早就造好了，我们
只负责读：

| 游戏机制 | HR 产物 | BRP 的工作量 |
|---|---|---|
| 工作站点方块 | 劳动合同 | 普查（Agent 扫描），零开发 |
| 补货 ≤2 次/日、每 offer 库存 ≈16 次 | 收入上限（构造意义上） | 经 `merchant.trade` 读取（docs/03 §10） |
| XP 等级（新手→大师） | 绩效考核与晋升 | 读取；**不做晋升体系** |
| 交易表（哪些 offer 存在） | 岗位说明书 | 改表 = 真正的权力，见下 |
| 僵尸化 → 治愈 → 折扣 | burnout；以永久折扣回聘（首轮最深 ◆，地板 1 绿宝石）——也是社区标准的长途调岗方案：僵尸化、押送、到岗治愈 ✅ | `villager.cured`（docs/03 §10） |

**岗位表。** 大厅编制跑在原版自己的机器上，BRP 只负责把手续归档。职类 =
职业（1.21 共 13 个在编工种），每个职类一张编制内收购岗、一组被从表里
编辑出去的高价值 offer——逐条 offer 数据 ◆，接线前对照 1.21.1 交易池核实：

| 职类 | 编制内收购岗（Java 1.21，wiki 已核 ✅） | 编制外（被编辑掉的） |
|---|---|---|
| 农民 | 20 小麦 / 26 马铃薯 / 22 胡萝卜 / 15 甜菜根 → 1 | 卖面包及更差的 |
| 牧羊人 | 18 羊毛 → 1 | 高职级收染料 |
| 制箭师 | 32 木棍 → 1；14 线 → 1（熟练工） | 卖弓——表外套利 |
| 渔夫 | 20 线 / 10 煤 → 1 | 卖船、附魔钓竿 |
| 屠夫 | 14 生鸡 / 7 生猪排 / 10 生牛肉 / 15 煤 → 1 | 卖熟肉 |
| 图书管理员 | 24 纸 → 1 | **附魔书——经验修补是套利岗，明令编制外** |
| 牧师 | 32 腐肉 → 1（就是牧师，已核实——我先前的屠夫猜想是错的 ✅） | 卖红石、荧石、经验瓶 |
| 三匠 | 15 煤 / 4 铁 / 燧石 / 熔岩桶 → 1；**1 钻石 → 1——只收原料** | 卖附魔钻石装备（大师镐与剑、大师头盔与胸甲）；在那花出去的每颗绿宝石都会重新铸出来——编制外 |

注意这条从真实机制里原样保存下来的残忍：岗位表收**钻石，永远不收钻石
工具**——成品装备在村民交易里根本不是一个品类，于是大厅里最高技能的劳动
在结构上不可计量。招聘启事承诺一个不存在的岗位、再按它开人，这不是讽刺；
这是把编号抹掉之后的制箭师 JD。

**职级职等。** 新手 → 学徒 → 熟练工 → 专家 → 大师（徽章：石头/铁/金/绿宝石/
钻石），经验阈值 0 / 10 / 70 / 150 / 250 ✅。晋升靠交易经验——你的对手方替
你涨薪；每一级都从下一档掷出新 offer，晋升即风险：大师掷烂了，死得比新手
贵。职等不是一个数字，它是治愈折扣——永久声望、首轮最深（1.20.2 起不再
叠加 ◆）、地板 1 绿宝石 ✅。大厅里没人说"职等"，他们说的是"折扣"——同一件事。

**KPI 的上限由管理层书写。** 把交易表逐件拿走——没有钻石工具（最高价值
品类根本进不了表）、没有经验修补（唯一暴利的套利，被编辑掉），直到只剩
线换绿宝石——"绩效"就只测一件事：搬砖搬得好不好。KPI 是设计出来的，
考核照着设计来。因此交易表的编排（重掷、禁用、锁定）才是劳动治理的真正
杠杆；末位淘汰只是这台杠杆下面的一场表演。编排是**版本化行为**：像 BOM
改版一样（docs/10 §4），岗位表是租户资产，改动可审计，而村民无权申诉。
劳动关系模块：不做——免责声明覆盖一切。

**淘汰显式化——大厅真实在跑的循环。** 真玩家从来不跟村民谈判，他们跑一个
重掷循环，和每个招聘经理跑的是同一个，只是没有 HR：

1. 放工位 → 无业村民认领 → 以新手入职，从职业池掷出两个 offer；
2. offer 不在表上 → 拆工位 → 村民落回无业（游荡、占床、不产出——普查会
   抓到这个漂移）→ 重放 → 重掷。重掷只在首次交易之前有效 ✅——经验一到
   offer 永久上锁。真正要紧的面试只有第一次；
3. 重掷预算耗尽（N 可配；大厅惯例 3–10 次；企业惯例："我们会再联系你"）
   → 不予录用；
4. 掷出合规 offer → 完成交易上锁，然后刷职级；
5. 之后的漂移或冗余 → 见下方处置。

每个出口都在 `villager.termination` 表单上带原因码，让表格决定谁走，
而不是恩怨：

- `C1 招不到` ——重掷预算耗尽（经验修补掷不出来的图书管理员都死在这）
- `C2 编制冗余` ——超 `villager` 配额（docs/03 §10），或抢工位清退：
  两个村民一张讲台，其中一个注定是个统计量
- `C3 结构无岗` ——傻子，永不认领工位 ✅。Java 不会生出傻子婴儿（那是基岩
  版的抽奖），但傻子成年后可以正常繁殖 ✅——永久编制挂进人才库：公司唯一
  允许他们的生产活动
- `C4 编制外 offer` ——岗位漂移，掷出或被治愈成表外交易；清洗 = 重掷到
  合规为止，即 C1 的内层循环，或者处置
- `C5 KPI 末位` ——末位淘汰，诚实条款见下

**末位淘汰，附统计学诚实条款。** 末位裁减按每村民 `merchant.trade` 吞吐对
L2 基线计算（05 §2）。在编排过的搬砖岗表下，p95/p5 产能比接近 1.0——当
比值 < 1.1 时，表单必须打印"排序无统计学依据，建议抽签"**并照样裁掉一个**。
这就是企业：仪式照跑，数据支不支持是数据的事。

**处置——玩家的真实做法，人类的手。** 目录止于玩家实践止步之处：BRP 不
发明机制，只把大厅已经在做的事归档，而且归档得更快。按升级顺序：

- **转岗** ——拆旧工位、放新工种：无业 + 重新认领是原版的岗位调配——
  顺带把治愈折扣清零，这是一次反向的降薪
- **回炉 / 冷链** ——僵尸磨坊：僵尸化 → 治愈 → 永久声望折扣，首轮最深 ◆，
  地板 1 绿宝石 ✅。offer **不**重掷——回炉买到的是价格，不是花样：每轮把
  员工变得更便宜，永不被开除，永不晋升，同一批 offer，同一条线。同一个
  僵尸态也是社区标准的长途搬运方案（夜间自走、可上船、到岗治愈 ✅）——
  PIP 和调岗服务是同一台机器
- **人才库** ——无业者进繁殖翼：预备劳动力，床位与口粮计量，每次出生按
  人头增长记入 `villager` 配额

斩杀**不在目录里**——村民是稀缺、慢再生的资源（没有繁殖机就几乎不可再生）；
任何 EHR 表单都不路由去岩浆，比这更黑的桥段都被考虑过并否决了。第三方
Incinerator 方块确实存在（Easy Villagers，02 §8）；BRP 计量其人口差并逐笔
记为未批准的资产减记。玩笑到此为止，奉旨截稿。

**手续。** 以上任何一种处置，都是一张带 C 码的 `villager.termination`
表单，进审批迷宫（§6），签字栏自带提交时算好的减记行——不是福利科目，
是资产科目：村民是稀缺人头，表单给损失定价，然后照签。执行永远是人类的手
（拆方块、开磨坊），Agent 只页、只计量、只记录，绝不执法（docs/03 §8 教义）。
本节没有任何新发明：拆工位就是解雇——结果是无业，不是傻子——BRP 唯一的
贡献是让手续比方块先到。

**普查 → `economy_daily`。** 三个状态，全部原版：**在雇**（认领工位、窗口内
有交易）、**预备**（无业与傻子——繁殖翼）、**冷链**（僵尸村民，调岗或 PIP
途中）。以及一条现实里的劳动者从未得到过的会计更正：村民不领工资、没有
预算——玩家为货物付给他们的绿宝石到手即销毁 ✅，所以**村民的收入就是玩家
的采购，而那是个汇**（docs/03 §10）。大厅里不存在"工作中的穷人"这个状态；
只有人头、吞吐和一张交易表。普查与鲸鱼税、CPI 同表并列，这才是真正的笑话。
